# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm install       # install dependencies
npm run dev        # Vite dev server (http://localhost:5173)
npm run build       # tsc -b (typecheck) then vite build -> dist/
npm run lint        # oxlint
npm run preview      # serve the production build locally
```

There is no test suite yet. There is no single-test command because there are no tests.

## Architecture

React 19 + TypeScript + Vite, styled with Tailwind CSS v4 (via `@tailwindcss/vite`, config lives in `src/index.css` under `@theme` — there is no `tailwind.config.js`) plus `framer-motion` for spring/cross-fade animation. `src/App.tsx` switches between three screens via local `useState<Screen>` (`"auth" | "character-select" | "game"`) — no router. `"auth"`/`"character-select"` share the static `NightSceneBackground`; submitting either auth form (no backend — purely a demo transition) advances the screen, and confirming a hero on character-select moves to `"game"`. The `"game"` screen is a different shell entirely: `DynamicBackground` (cross-fading per-tab scene) behind a `<main>` that renders the active tab's screen, with `BottomNav` fixed at the bottom; `activeTab: TabId` is separate state that both `DynamicBackground` and `BottomNav` read.

- `src/components/background/NightSceneBackground.tsx` — the animated pixel-art scene (night skyline, moon, twinkling stars, lampposts with reflected glow, shimmering water). Pure SVG (`shapeRendering="crispEdges"` for the pixel look) plus a few absolutely-positioned HTML spans for glow/firefly effects; CSS keyframes for the animations live in `src/index.css` (`.animate-twinkle`, `.animate-lantern`, `.animate-water`, `.animate-float-up`) and respect `prefers-reduced-motion`. Star positions are generated once via a seeded PRNG in `starfield.ts` so the field doesn't reshuffle on re-render. A PixelLab-sprite version of this scene was tried and reverted — the generated building sprites didn't share a consistent scale/style with each other, so this stays hand-coded SVG/CSS. Don't retry that without solving the style-consistency problem first (e.g. `style_character_id`/reference-image matching isn't available for `create_map_object`).
- `src/components/auth/` — `AuthCard` (glassmorphism container, owns which tab is active, takes an `onAuthenticated` callback), `TabSwitcher` (Connexion/Inscription pill toggle), `LoginForm`, `RegisterForm`. Each form owns its own local state/validation and calls an optional `onSubmit` prop.
- `src/components/character/` — the character-select screen. `CharacterSelectScreen` owns `gender`/`selected` state (lazily initialized from `localStorage["pixelrmmo:hero"]`, no effect) and renders `GenderToggle` (♂/♀ pill, same sliding-pill pattern as `TabSwitcher`) plus a responsive grid of `ClassCard`. Class data (stats, passive, sprite imports, per-role color theme) lives in `src/data/classes.ts`, one `ClassDefinition` per class with a `sprites: Record<Gender, string>` map — confirming a hero persists `{classId, gender}` to `localStorage`. `ClassCard` idles via a looping breathing animation and plays a short attack animation via `AnimatedSprite` (in `src/components/ui/`) whenever the card is clicked (selection + attack trigger on the same click, resuming the idle loop afterward).
- `src/components/ui/` — presentational primitives: `TextField`, `PasswordField` (show/hide toggle), `Checkbox`, `Button`, `StatBar` (labeled gauge used by `ClassCard`), `AnimatedSprite`. `AnimatedSprite` layers two independent loops: `idleFrames` cycles continuously whenever `playing` is false (own `setInterval`, ~220ms/frame — falls back to the static `idleSrc` if empty), and `attackFrames` plays once through when `playing` flips true, then hands control back to the idle loop via `onFinish`. Both frame arrays are preloaded with `new Image()` on mount to avoid flicker on first play/first loop tick.
- `src/assets/characters/*.png` — 6 PixelLab-generated character sprites (south-facing rotation, transparent background), one per class×gender pair, generated via `mcp__PixelLab__create_character` (mode `standard`, `view: "side"`, same detail/shading/outline/proportions params across all 6 for a consistent look). Unlike the background scene, isolated character portraits compose fine since each card only shows one sprite at a time with no shared-scene blending needed.
- `src/assets/characters/attacks/*.png` — 8-frame attack animations (one set per class×gender, `{class}-{gender}-{1..8}.png`), generated via `mcp__PixelLab__animate_character` with `mode: "v3"`, `directions: ["south"]` (only the direction the card displays), and a per-class `action_description` (sword swing / bow draw+release / staff or orb cast) rather than a generic template — v3's free-text description lets the animation match the weapon already drawn on the static sprite. `classes.ts` picks these up automatically via `import.meta.glob("../assets/characters/attacks/*.png", { eager: true })` keyed by filename prefix (`getAttackFrames("knight-male")` etc.), so dropping in new `{prefix}-{n}.png` files is enough — no import list to maintain. A `ClassDefinition` whose gender has no frames yet just gets `attackFrames: []`, and `ClassCard`/`AnimatedSprite` no-op instead of erroring.
- `src/assets/characters/idle/*.png` — 4-frame idle-breathing loops (one set per class×gender, `{class}-{gender}-{0..3}.png`, frame 0 included since these came from `mode: "template"` rather than v3), generated via `mcp__PixelLab__animate_character` with `template_animation_id: "breathing-idle"` (a proper PixelLab template — cheap at 1 generation/direction and reliably loops cleanly, unlike a custom `action_description` which is the right call for a one-off combat move but not needed here), `directions: ["south"]` only. `classes.ts`'s `getIdleFrames(prefix)` collects these the same glob-by-prefix way as `getAttackFrames`, starting the numbering at 0 instead of 1.
- `src/data/tabs.ts` — the 5 game tabs (`TabId = "camp" | "dungeon" | "bestiary" | "crafting" | "market"`; `"crafting"` covers the forge plus (eventually) cooking, jewelry, etc. — not just blacksmithing, hence the name), each with a label, its full-scene `background` image import from `src/assets/scenes/*.png`, and `frames: string[]` — a looping idle-animation sequence for its nav icon. Frames are collected automatically via `import.meta.glob("../assets/icons/nav/anim/*.png", { eager: true })` keyed by filename prefix (`getNavFrames("camp")` → `[camp-0.png, camp-1.png, ...]`, in numeric order, stopping at the first gap), so dropping in new `{prefix}-{n}.png` files is enough — no per-tab import list to maintain. Both `BottomNav` and `DynamicBackground` iterate/read this single list, so adding a tab means adding one entry here (plus a `COMING_SOON` copy line in `App.tsx` if it has no real screen yet).
- `src/components/background/DynamicBackground.tsx` — fixed full-bleed background for the `"game"` shell. Renders the active tab's scene image inside `AnimatePresence` (default `mode="sync"`, not `"wait"` — that's what makes both the outgoing and incoming image fade simultaneously for a true cross-fade instead of a fade-out-then-fade-in). A dark radial vignette + flat overlay sit on top for text legibility, same trick as `NightSceneBackground`.
- `src/components/nav/BottomNav.tsx` — fixed bottom tab bar, `paddingBottom: env(safe-area-inset-bottom)` for iOS/Android safe areas. No dome/pill indicator behind the icon (a first version had a floating circular "dome" — even after fixing its centering bug it still looked bad and was cut per explicit feedback); the active tab is instead marked by the icon lifting slightly + a gold glow, plus a thin sliding underline (`motion.span` with `layoutId="activeTabUnderline"`) below the label. Tab icons play a continuous idle loop: one shared `setInterval` in `BottomNav` increments a `tick` counter, and each tab indexes into its own `tab.frames` with `tick % frames.length` — one interval driving all 4 icons rather than 4 independent timers. If you reintroduce any kind of active-tab background shape, remember an absolutely-positioned element with no `left` set is NOT auto-centered — it renders at its static-position left edge (`left-1/2 -translate-x-1/2` is required to center it), which is what made the original dome look like an off-center smear.
- `src/components/camp/CampScreen.tsx` — the `"camp"` tab's content: Écus/€ header, hero panel (animated idle sprite + level + username + PV `StatBar` + 3 equipment slots, read from `localStorage["pixelrmmo:hero"]` via `classes.ts`), a 16-slot backpack grid (starter weapon/armor/2 potions filled, rest empty placeholders) with a tap-to-toggle tooltip per filled slot, and a "Donjon 1" access card. The `username` prop (displayed as `@{username}` under the hero's class name) is threaded down from `App.tsx`, which captures it from whichever auth form the player submitted (`LoginForm`'s `identifier` or `RegisterForm`'s `username`, passed up through `AuthCard.onAuthenticated(username)`) and persists it to `localStorage["pixelrmmo:username"]` — there's still no backend, so this is just what the player last typed, not a validated account name. Starter weapon AND armor are per-class (`STARTER_WEAPON`/`STARTER_ARMOR` maps keyed by `ClassId`, each with a name + a PixelLab item-icon import) so a Knight/Archer/Mage each see their own gear instead of one generic set. The backpack grid has `max-h-[300px] overflow-y-auto` — capping its height (instead of letting 4 rows of mostly-empty slots stretch the page) is what keeps the whole screen short enough that the fixed `BottomNav` doesn't cover the dungeon card on shorter (~900px) desktop viewports. Because that container clips overflow on both axes, item tooltips open *below* the icon (`top-full`, not `bottom-full` — the only real items sit in row 1, so opening upward clipped them against the container's top edge) and use per-column horizontal anchoring (`left-0` / centered / `right-0` by `i % 4`) instead of always centering, so the edge-column tooltips don't get clipped sideways either. Equipment/backpack data here is presentational demo state, not wired to any inventory system yet.
- `src/components/camp/HeroProfileOverlay.tsx` — fullscreen hero profile card, opened by tapping the avatar in `CampScreen`'s hero panel. The avatar's `motion.button` in `CampScreen` and the overlay's `motion.div` share `layoutId="hero-avatar-frame"`; the small button is conditionally *unrendered* (not just hidden) while the overlay is open, so framer-motion's shared-layout matching animates the FLIP between the small card slot and the fullscreen center position automatically — no manual position math, no wrapping `LayoutGroup` needed since there's only ever one of the two mounted at a time. The overlay shows a class/gender `profileBackground` behind a bigger `AnimatedSprite`, the class's existing `stats`/`passive` (reused from `classes.ts`, not duplicated), and a demo level/XP bar (`DEMO_LEVEL`/`DEMO_XP` constants — there's no real leveling system yet) that animates its width in on open. Closes on backdrop click or the ✕ button.
- `src/components/codex/CodexHub.tsx` — what the `"bestiary"` tab actually renders: a "Grand Codex du Royaume" with its own sliding-pill sub-switcher (same `TabSwitcher` pattern, inlined rather than reused since it needs custom tab content) between `Bestiary`, `MaterialsCompendium`, and `TypeMatrixCompendium`. Owns the cross-linking between the first two sub-tabs in *both* directions, each following the identical pattern: `jumpToMonsterId` is set when a material's provenance button is clicked (`MaterialsCompendium`'s `onViewMonster`, fired from `MaterialCard`, `MaterialModal`, *and* `TypeMatrixCompendium`'s monster list — all three share the same `viewMonster` closure) — flips the sub-tab to `"bestiary"` and passes the id down as `Bestiary`'s `requestedMonsterId` prop; `jumpToMaterialId` is the mirror image, set when a monster's loot-table row for a linked material is clicked (`Bestiary`'s `onViewMaterial`, threaded down into `MonsterModal`) — flips to `"materials"` and passes `requestedMaterialId` into `MaterialsCompendium`. `TypeMatrixCompendium` only ever *sends* jumps (to Bestiaire), nothing jumps into it yet, so it doesn't need a `requested*Id`/`onRequestHandled` pair of its own. Because `CodexHub` conditionally renders only the active sub-tab, the *other* screens fully unmount whenever one is showing, so a `requested*Id` only ever arrives on a *fresh* mount — both `Bestiary` and `MaterialsCompendium` consume theirs as a lazy `useState` initializer for `selectedId` (not an effect that calls `setSelectedId`, which would also require guarding against the request re-firing on every future mount, e.g. from the player just tapping the tab pill directly afterward). A separate empty-deps effect on each fires its `onRequestHandled` once on mount to clear the id in `CodexHub`, so a *direct* tab-pill click later doesn't reopen the same modal.
- `src/components/bestiary/` — the Bestiaire sub-tab: a searchable/filterable collection-card grid of the 20 Crypte Ancestrale monsters. `Bestiary.tsx` owns `search`/`filter`/`selectedId` state and renders the family filter pills (`Tous`/`Vermines`/`Squelettes`/`Spectres`/`Gardiens & Rares`/`Boss & Élites`, counts computed from `BESTIARY.length`) plus a responsive `grid-cols-2 sm:grid-cols-3 lg:grid-cols-4` of `MonsterCard`. Tapping a card opens `MonsterModal` (full stats/skill/lore/loot-table) via the same "shared layoutId, unrender the small instance while the twin is open" FLIP pattern as `HeroProfileOverlay` — `MonsterCard` takes an `isOpen` prop and renders an inert placeholder div (no `layoutId`) instead of the real button when its modal twin is mounted, so the two never coexist with the same `layoutId`. Both the card and modal reuse one posture toggle (`👁️ Repos` / `⚔️ Attaque`, local `useState`, not lifted) that just swaps which frame array (`idleFrames` vs `attackFrames`) is passed into `AnimatedSprite` — both loop continuously, so no `playing`/`onFinish` wiring is needed (unlike the class-select attack-on-click pattern). `theme.ts` maps each of the 5 families to a border/accent/glow color and each of the 4 rarities to a badge color + whether the badge pulses (`RarityBadge.tsx` — only `rare`/`miniboss`/`boss` pulse; `normal` stays static so 15 of 20 cards aren't animating at once).
- `src/components/codex/MaterialsCompendium.tsx` + `MaterialCard.tsx` + `MaterialModal.tsx` + `RarityFrame.tsx` — the Livre des Matériaux sub-tab: category filter pills (`Tous`/Forge/Alchimie/Enchantement/Reliques) and 8 rarity-tier filter badges (colored from `RARITY_BY_ID`, toggle on/off — clicking the active one clears it back to "all") drive a `MaterialCard` grid. `MaterialCard` follows the exact same `isOpen`-placeholder FLIP pattern as `MonsterCard`/`MonsterModal` (`layoutId={"material-card-" + id}`, shared with `MaterialModal`) — tapping anywhere on the card opens the modal. Each card's provenance row is a *separate* nested `<button>` calling `onViewMonster(material.provenance.monsterId)` with `e.stopPropagation()` (both on the card and inside the modal), which is how the CodexHub jump-to-bestiary wiring gets triggered without also opening this card's own modal. `RarityFrame` grew a `layoutId`/`onClick` pair to support this: when `onClick` is passed it renders the bordered wrapper as `motion.button` instead of `motion.div`, so both `MaterialCard` and `MaterialModal` can share one component for "what does this rarity tier look like" *and* the click/FLIP behavior, rather than duplicating the tier-effect logic. `RarityFrame` is the shared "how does this rarity tier look" wrapper (used around each material icon/card) — it escalates by tier rather than being 8 independent styles: tiers 1-2 (Poor/Common) get only a static border ± a faint non-animated shadow, tiers 3-5 and 7 (Uncommon/Rare/Epic/Legendary) get `.animate-rarity-pulse` (a `box-shadow` breathing glow, `--glow-color`/`--dur` as CSS custom properties so one keyframe serves all four at different speeds/colors — Legendary just runs slower/richer via its own `PULSE_DURATION` entry), tier 6 (Mythic) swaps to `.animate-rarity-flicker` (an irregular multi-stop keyframe suggesting flame rather than a smooth pulse), and tier 8 (Transcendent) gets `.animate-rarity-prismatic` (a dedicated keyframe layering three fixed-color shadows — cyan/violet/gold — since a single `--glow-color` var can't express multiple hues) plus 5 small `.animate-twinkle` sparkle dots overlaid (the exact same star-twinkle mechanism/CSS vars as `NightSceneBackground`'s starfield, reused rather than reinvented). All the new keyframes live in `src/index.css` alongside the existing scene ones and are included in the same `prefers-reduced-motion: reduce` kill-switch block. An earlier version tried a rotating conic-gradient ring (masked down to a thin border via `mask-composite`) for Legendary/Transcendent — abandon that approach if you're tempted to reintroduce it: a conic-gradient's angular sweep projected onto a *tall rectangular* card (not a square icon) reliably produced a stray diagonal streak cutting across the card content in Chromium, and it survived multiple mask-property fix attempts, so it was replaced outright with the shadow-layering technique above rather than chased further.
- `src/data/rarity.ts` — the 8-tier rarity system (`RarityId = "poor" | "common" | "uncommon" | "rare" | "epic" | "mythic" | "legendary" | "transcendent"`), each with an exact hex `color` (not a Tailwind palette name — the design spec gave precise hex values per tier that don't map onto Tailwind's defaults, so `RarityFrame`/`MaterialCard`/the rarity filter pills all consume `color` via inline `style`, not utility classes) and a `tier: number` (1-8) that `RarityFrame` branches on for which visual treatment to apply. This is a *different* rarity concept from `bestiary.ts`'s `MonsterRarity` (`normal`/`rare`/`miniboss`/`boss`, monster threat level) — they're deliberately not unified since one describes crafting-material quality and the other describes combat difficulty.
- `src/data/bestiary.json` + `src/data/bestiary.ts` — the monster data is split in two: the `.json` is pure data (stats, skill, lore, `drops[]` with `chance`/optional `currency`+`min`/`max`), hand-authored from the game design doc so it has no PixelLab/asset knowledge at all. `bestiary.ts` imports that JSON, glob-loads `portraits/idle/attack` assets the same way `classes.ts` does (`getFrames(modules, id)` collects `{id}-0.png, {id}-1.png, ...` in order, stopping at the first gap), and merges them onto each entry as `MonsterDef`. All 4 core gauges (PV/ATK/DEF/VIT) are normalized against one shared `STAT_SCALE` (`{hp:600, atk:36, def:24, speed:5}`, i.e. the boss's own numbers) so a card's bar length is meaningful relative to *every* monster in the bestiary, not just within that one card — a Level 1 rat's PV bar reading as visibly tiny next to the Skeleton King's is intentional. Monsters without an explicit "Vitesse" stat in the design doc (e.g. `bone_spearman`'s "Portée: Allongée") got an inferred `speedLabel`/`speedValue` so every card still has all 4 gauges, with the actually-named special stat preserved in `extraStats` (numeric, e.g. Parade/Critique — rendered as a 5th gauge in the modal) or `traits` (text-only, e.g. "Portée Allongée" — rendered as a plain badge). Individual `drops[]` entries carry an optional `materialId` linking them to a `materials.ts` id — this was back-filled by cross-referencing the two datasets after the fact (they were authored in separate passes with slightly different names/percentages for what's conceptually the same drop, e.g. bestiary's "Aile membraneuse" vs materials' "Aile Membraneuse Impeccable"), so the bestiary-side name/chance were realigned to match the material's canonical values wherever a link exists, and two materials that had no corresponding bestiary row at all (`brittle_bone` off `plague_rat`, `rusty_scrap` off `skeleton_recruit`) got new rows added rather than left dangling. `MonsterModal`'s loot rows only get an icon + become clickable (calling `onViewMaterial`) when `materialId` is set (via `MATERIAL_BY_ID`) or the drop is currency (the real `ecuIcon` PNG, not a 🪙 emoji, matching every other Écus display in the app) — a flavor-only drop like "Épée ébréchée" that has no linked material renders as plain text, on purpose, rather than getting a fake/generic icon. Every monster also carries a `combat: MonsterCombat` object (`typeLabel`, `combatTypes`, `weaknesses`, `resistances`, `immunities`, `inflicts`) for the Types & Météo matrix — `typeLabel` is a free-text flavor string straight from the design doc (e.g. "Ombre / Bête") and isn't necessarily one of the 7 canonical `DamageTypeId`s, while `combatTypes` is a separately editorially-assigned array of actual canonical type ids, because the matrix/filter UI needs exactly 1-2 real types per monster to group and filter by and the flavor label alone can't reliably provide that.
- `src/assets/bestiary/portraits/{id}.png` (128×128, 160×160 for the two largest bosses), `src/assets/bestiary/idle/{id}-{0..3}.png` (4 frames), `src/assets/bestiary/attack/{id}-{0..6}.png` (7 frames) — all generated via a `create_image_pixflux` (static portrait) → `animate_image` ×2 (idle loop, attack loop) pipeline, **not** `create_character`/`animate_character`. The bestiary only ever shows a monster from one fixed angle (a trading-card portrait), so there's no need for `create_character`'s multi-direction rig — and `animate_image` works on *any* loose sprite regardless of anatomy, which matters a lot here since most of these 20 creatures (a floating flame, a giant spider, a living shadow, a treasure chest with a mouth) don't fit `animate_character`'s humanoid/quadruped skeleton templates at all. `animate_image`'s `first_frame_url` is always the *original* portrait job's download URL, not a re-upload, so idle and attack both start from the same source frame. Two prompt-quality traps came up empirically and are worth avoiding: a `create_image_pixflux` description implying an "RPG monster portrait" alone can hallucinate a stray human silhouette or a copyright-style watermark string baked into the pixels (same failure mode as the profile-bg scenes, see below); a description that's otherwise fine still needs "front-facing" and a consistent `view: "side"` across all 20 or the poses drift. PixelLab enforces a hard cap of **8 concurrent jobs** across the whole account (a 9th `create_image_pixflux`/`animate_image` call fails outright with a rate-limit error, it doesn't queue) — generating this many assets means firing in batches of ≤8, polling with `get_image`, downloading/freeing a slot, and immediately backfilling rather than firing all ~65 jobs at once.
- `src/data/materials.json` + `src/data/materials.ts` — same split as `bestiary.json`/`bestiary.ts`: the JSON is pure hand-authored data (name, `rarity: RarityId`, `category`, `usage`, `lore`, `provenance: {monsterId, dropChance}` — `monsterId` is a real `bestiary.ts` id, which is what makes the card's provenance button clickable/navigable, `value` in Écus), and `materials.ts` glob-loads `src/assets/materials/icons/{id}.png` the same `getIcon`-by-filename way `bestiary.ts` does portraits, defaulting to `""` for any id with no icon generated yet so the grid never throws on a partial asset set. `CATEGORY_LABELS`/`CATEGORY_ICONS` map the 4 `MaterialCategory` values to their French label + emoji for the filter pills.
- `src/assets/materials/icons/{id}.png` (32×32, `no_background: true`) — generated via `create_image_pixflux` only (no animation pass — these are static inventory icons, not cards with a posture toggle), `detail: "medium detail"` rather than "highly detailed": at 32px, PixelLab's higher detail settings produce icons that read as noisy/illegible rather than more refined, so the lower setting was deliberately picked for this asset size (contrast with the 128px+ bestiary portraits, which do use "highly detailed"). One reroll was needed here too: `shadow_essence`'s first pass ("shadow essence orb" with a "red-tinged" hint) came out as a bright pink teardrop rather than reading as dark/shadowy at all — descriptions for anything conceptually "dark" need to explicitly anchor the base color ("solid black... with a faint red inner glow") rather than trusting a single adjective to carry it.
- `src/assets/characters/profile-bg/{class}-{gender}.png` (384×400 portrait, one per class×gender combo) — the `HeroProfileOverlay` backdrops, generated via `mcp__PixelLab__create_image_pixflux` with a per-class theme (knight = blue-lit castle courtyard, archer = emerald misty forest, mage = violet arcane sanctum) and a *different seed/framing per gender* within the same class so all 6 are distinct while staying visually consistent per class. Explicitly prompt "no people, no characters, no silhouettes, no text, no watermark, no logo" — without that, pixflux tends to hallucinate a human silhouette standing in the scene (which visually collides with the real character sprite drawn on top) or a stray copyright-style watermark string baked into the pixels; both slipped through on the first pass here and needed a reroll.
- `src/assets/scenes/*.png` (400×224, one per tab), `src/assets/icons/ecu.png` (64×64 Écus coin), `src/assets/icons/items/*.png` (64×64 weapon/armor/potion/skull item icons) — generated via `mcp__PixelLab__create_image_pixflux` (freeform scene/icon generation, no character rig, `no_background: true` for icons). `create_image_pixflux`'s max canvas is 400×400 and both dimensions must be divisible by 4 at that size (400×225 is rejected, 400×224 works). Unlike the reverted map-object skyline, these are single flat images (no compositing of separate sprites into one scene), so the style-consistency problem from that attempt doesn't apply here.
- `src/assets/icons/nav/anim/{tab}-{0..4}.png` (48×48, 5 frames per tab: `-0` is the original static icon, `-1..-4` are generated) — the nav icons are *animated*, not static: generated via `mcp__PixelLab__animate_image` (not `animate_object`/`animate_character` — those need an id of something PixelLab already rigged, while `animate_image` works on any loose sprite, which is what `create_image_pixflux` output is), `frame_count: 4` ("4 for idle loops" per the tool's own guidance — plenty for a small ambient loop like a waving flag or a swaying scale, no need for 8+), passing the original icon's `first_frame_url` (the stable `https://api.pixellab.ai/mcp/images/<job_id>/download` API URL, not a signed/expiring one) and a motion-only `action` description (e.g. "small flag on top of the tower gently waving in the wind" — describe the movement, not the subject, since the subject is already in the reference frame).
- `src/data/types.json` / `statuses.json` / `weather.json` + `src/data/typeSystem.ts` — the Types & Météo sub-tab's data, split the same JSON-is-pure-data/`.ts`-is-the-loader way as `bestiary`/`materials`. `types.json` holds the 7 canonical damage types (`DamageTypeId = "fire" | "ice" | "lightning" | "nature" | "holy" | "shadow" | "physical"`), each with a `strongVs: DamageTypeId[]` list — a hand-invented-from-scratch effectiveness chart (the design spec gave per-monster weaknesses but not an explicit type-vs-type table), derived by pattern-matching which types recurred most across the concrete per-monster `combat.weaknesses` data, e.g. Sacré shows up as a weakness on almost every undead/shadow monster so `holy.strongVs` includes `shadow`; heavy Foudre-weakness on armored monsters gives `lightning.strongVs` → `physical`. `typeSystem.ts` derives the inverse table, `WEAK_VS_BY_ID` (what each type is *weak against*), by filtering all types for whose `strongVs` includes it — kept as a derived export rather than hand-authoring both directions, so the two can never drift out of sync. `statuses.json` holds the 8 status effects (`category: "dot" | "control" | "debuff" | "buff"`, plus a `formula` string shown verbatim in the UI, e.g. "3 dégâts/sec pendant 5s (cumulable x2 max)" — these per-second numbers are reinterpreted into discrete per-turn ticks by `battleEngine.ts`'s `STATUS_DURATIONS`/`STATUS_MAX_STACKS`, see below, since there was no combat system to consume them yet when this sub-tab was built). `weather.json` holds the 6 weather states, each with a `modifiers: {label, value}[]` list rendered as pills on the active-weather banner. All three loaders glob-load their badge from `src/assets/codex/badges/{types,statuses,weather}/{id}.png` via the same `getBadge`-by-filename pattern as `bestiary.ts`'s `getPortrait`. The weather cycle is a deterministic wall-clock timer with zero server state: `getActiveWeatherIndex(now)` is `Math.floor(now / WEATHER_CYCLE_MS) % WEATHER.length` (10-minute cycle), so every client independently lands on the same active weather and countdown just from `Date.now()` — no polling, no backend, no drift to reconcile.

- `src/data/battleEngine.ts` — the turn-based combat rules, as pure functions operating on a `Combatant[]` array (no classes, no hidden state) so `TurnBattleArena` can drive them from a plain async loop. `buildHeroCombatant`/`buildEnemyCombatant` normalize hero and monster into one `Combatant` shape; `computeDamage` implements the spec'd `(ATK×power − DEF) × typeEffectiveness × weatherModifier` formula (dodge/block rolled first, either fully negates; a min-1-damage floor unless the target is flatly immune). `HERO_BASE_COMBAT` (ATK/DEF/Vitesse per class) is entirely invented — `classes.ts`'s own `stats` array is percentage/display stats (Armure, Critique, Pénétration Magique...) with no numeric combat triad — and **was headlessly simulated and rebalanced before shipping**, not just eyeballed: an initial pass around ATK 16-24 left every class's *basic* attack floored to 1 damage against the boss's DEF 24 (`ATK − DEF ≤ 0`), making wave 3 mathematically unwinnable regardless of play quality. Confirmed by running a few thousand simulated dungeon runs — see the testing note below — then retuned (higher ATK across the board, a small innate "arcane evasion" dodge for Mage since it's the only class with neither an Esquive nor Parade display stat to derive one from, Mage's skill mana cost cut 25→15) until all three classes cleared with reasonable-but-not-guaranteed win rates against a deliberately unoptimized bot. When Chevalier's kit later lost its holy damage skill in favor of a pure-defense one (see `skills.ts`), its simulated win rate collapsed to 0% even though nothing else changed — losing the *only* skill capable of a weakness-multiplier hit against this dungeon's undead roster (its physical basic attack never procs "Super Efficace" against anything here) meant Chevalier's entire damage output was now a single flat number with no upside, so `HERO_BASE_COMBAT.knight.atk` was raised again (35→50) until simulated win rate recovered into the same healthy range as before the kit change. The lesson generalizes: any change to a class's *kit*, not just its raw numbers, needs a re-run of the same headless simulation before shipping — a skill swap that reads as a lateral trade on paper can be a hidden nerf once the type-effectiveness math is actually exercised. Current numbers land around Chevalier ~25-30%, Archer ~60-65% (its `freeze` proc chain-locking enemy turns matters more than raw damage), Mage ~10-15% (lowest HP, stays hardest on purpose but not a brick wall).

## Notes

- The `claude/pixellab-mcp-integration-vajrla` branch name refers to a PixelLab (pixellab.ai) MCP server registered for asset generation; it's connected and reachable from this environment. Use `mcp__PixelLab__create_character` for character/portrait sprites (works well) — see the caution above before using `create_map_object` for anything that needs to visually blend into one composed scene.
- The Google Fonts `@import` in `src/index.css` (for `Press Start 2P`) fails in network-restricted sandboxes (`fonts.googleapis.com` blocked) and silently falls back to the system sans stack — this is expected to work in normal deployments/browsers.
- Headless-testing pure game logic (`battleEngine.ts`/`waves.ts`/`lootEngine.ts`) can't just be `node script.js`'d directly: those files (and everything they import — `bestiary.ts`, `materials.ts`, `classes.ts`...) use `import.meta.glob`, a Vite-only construct that throws outside Vite's transform. Neither `tsx` nor `vite-node` is installed, and this project deliberately has no test suite/runner to add one for. The workaround that worked: launch a real `chromium` (Playwright, already available in this environment — see the top-level environment notes) pointed at the running `npm run dev` server, then `await import("/src/data/battleEngine.ts")` etc. *inside* `page.evaluate` — the dev server serves those paths as real Vite-transformed ES modules, so the actual shipped code runs, `import.meta.glob` and all, at full speed with no per-turn UI timers slowing it down. That's how the hero-stat balance pass (see `battleEngine.ts` above) ran a few thousand simulated dungeon clears in seconds to catch the "boss DEF floors every basic attack to 1 damage" bug empirically rather than by manual arithmetic, and it's a reusable pattern for validating any future pure-logic change the same way before touching the slower live-browser pass.
